# Internationalization and RTL

## Product requirement and current state

ETripleSoft Learn is a bilingual English/Arabic product. Both languages are core requirements. The application uses shared English and Arabic routes and feature components. Application interface text is stored in locale message resources. LMS content uses database translation records where its domain is implemented; the local/CI Odoo Development fixture now includes explicitly labeled demo translations in both locales. Other course and short-lived demo fixtures remain English unless noted.

| Locale | Language | Direction |
| --- | --- | --- |
| `en` | English | LTR |
| `ar` | Arabic | RTL |

The initial default locale is `en`. Locale types should be explicit (`"en" | "ar"`) rather than unrestricted strings.

## Planned localization solution

The restructuring will introduce `next-intl` for:

- locale routing and locale-aware links/switching
- application UI messages in Server and Client Components
- date and number formatting
- pluralization

The implementation uses `next-intl` v4 with Next.js 16 Proxy routing, a locale-prefixed route tree, and shared locale-aware navigation helpers. Locale detection follows the URL only; an unprefixed route resolves to English.

## Target routing and document direction

Application pages will live under `src/app/[locale]/`, with shared route pages and components. Route groups such as `(learner)` and `(auth)` remain URL-neutral. For example, `src/app/[locale]/(learner)/courses/page.tsx` produces `/en/courses` or `/ar/courses`.

The locale layout will validate the supported locale and set the document attributes centrally:

```html
<html lang="en" dir="ltr">
<html lang="ar" dir="rtl">
```

The root URL `/` redirects to `/en`. Existing non-localized paths resolve to their English equivalents; `/overview` resolves to `/en/overview`. Auth pages and callbacks preserve the URL locale, and an explicit `/en` or `/ar` route remains authoritative over stored `preferred_locale`. See [ROUTES.md](ROUTES.md). The locale layout sets document language and direction centrally.

## Shared components and messages

Use one page/component and feature implementation per experience, with localized content and direction-aware presentation. Do not create parallel `components/en/` and `components/ar/` trees or language-named copies such as `EnglishCourseCard` and `ArabicCourseCard` unless product requirements establish genuinely different experiences that cannot reasonably share a component.

Application interface labels, actions, navigation, status messages, and form copy belong in `next-intl` messages. Organize keys by domain, for example:

```json
{
  "common": {},
  "navigation": {},
  "dashboard": {},
  "courses": {},
  "assessment": {},
  "calendar": {},
  "certificates": {},
  "settings": {},
  "auth": {},
  "checkout": {},
  "ai": {}
}
```

Maintain corresponding English and Arabic resources in `messages/en.json` and `messages/ar.json`. Extract hardcoded UI text feature by feature; avoid a massive uncontrolled search-and-replace and repeated locale ternaries.

Use Modern Standard Arabic for the Arabic interface. Arabic formatting retains Western digits (`latn`). Do not store the body of lessons or substantial LMS material in message JSON. Existing course, lesson, question, answer-option, instructor, and event fixtures remain English demo content except for the explicitly labeled local/CI Odoo Development module and lesson translations. Keep lesson content in the database fixture, separate from UI message resources.

## UI translations versus LMS content

**Application UI** includes labels such as Dashboard, Courses, Settings, Continue Learning, Next, Previous, Start Assessment, Save, and Cancel. These are message resources.

**LMS content** includes course and module titles, descriptions, lesson titles and bodies, instructor content, quiz questions, and answer choices. The Phase 07/08 schema provides per-locale course, module, and lesson translation records, and requires exact-locale publication where those domains are used. Quiz/question localization remains future work with the assessment domain. The Odoo Development lesson material in the local/CI fixture is assistant-authored demo content, not original ETripleSoft course material.

## RTL and CSS behavior

- Prefer logical CSS properties when they match the intent: `margin-inline-*`, `padding-inline-*`, `border-inline-*`, `inset-inline-*`, `text-align: start/end`, `inline-size`, and `block-size`.
- Review existing physical `left`/`right` values contextually. Do not mechanically rewrite every physical property or create a giant stylesheet of `[dir="rtl"]` overrides.
- Use explicit, component-scoped RTL adjustments only where direction changes meaning or composition. Keep shared design-system behavior where possible.
- Review navigation, sidebars, breadcrumbs, previous/next controls, pagination, step progression, and icon/text order for directional meaning.
- Classify icons as directional or non-directional. Directional arrows and chevrons may need adaptation. Do not automatically mirror logos, company/product brands, screenshots, photos, video, charts whose meaning changes, play/download icons, or generic non-directional icons.

## Arabic typography and mixed-direction content

**Decision (2026-10-08, D09 font source):** Arabic uses IBM Plex Sans Arabic, self-hosted in `public/fonts` (SIL OFL, `IBM-Plex-OFL.txt`), chosen from a comparison of Cairo, Tajawal, Noto Sans Arabic, Readex Pro and Almarai. `src/arabic-font.css` declares it as `Plex Arabic` with an Arabic-script `unicode-range`, so Latin text and digits keep the existing fonts (Learn/Inter in the learner app; Canva Sans/Montserrat on the public site). Eight-width visual sign-off and native-speaker review are still open.

The bundled Inter font was reviewed at 1280px with Arabic interface copy and looked readable for glyphs, line height, wrapping, and controls. Its embedded Arabic coverage versus system fallback has not been confirmed, and all-width visual review remains open; Arabic font sign-off is pending. Do not carry Latin letter spacing into Arabic without explicit validation.

Arabic interface copy should be natural and terminology-consistent, not word-for-word substitution. Allow for translated text expansion. Technical names such as Odoo, Python, PostgreSQL, API, and CRM may remain in their expected form. Use appropriate bidirectional isolation/direction for embedded English terms, code, URLs, IDs, email addresses, and phone values; do not blindly set every form value RTL.

## Locale-aware formatting

Use the localization layer and locale-aware APIs for dates, times, numbers, counts, percentages, and currency. Do not assemble localized values by concatenating fragments. Arabic uses Western digits. USD demo prices remain USD and are formatted for the active locale.

## Forms and controls

Verify RTL labels, field layout, validation messages, icon placement, dropdowns, password visibility controls, focus order, and touch targets. Email addresses, URLs, code, and identifiers may need LTR value direction inside an RTL form. Directional actions must retain their intended meaning and accessible names.

## Metadata and public pages

Localized pages provide locale-specific title and description, canonical URLs through the Next.js Metadata API, and alternate locale links through `next-intl` routing.

## Future LMS behavior

- **AI assistant:** Keep interface locale, source/course language, and requested response language as separate concepts. For example, the interface can be Arabic, course material English, and the requested response Arabic. Retrieval language must not dictate answer language.
- **Assessments:** Scoring, correct-answer identity, passing percentage, attempts, timers, and retry rules remain language-independent business logic. Question and option presentation may be localized independently.
- **Certificates:** Preserve the ability to select a certificate locale later. English, Arabic, or bilingual certificate output has not yet been decided.
- **Database:** The initial Supabase foundation stores an owner-scoped preferred locale constrained to `en`/`ar`. Phases 07/08 add course, module, and lesson translation tables separately from UI messages. The local/CI Odoo Development fixture exercises English and Arabic course curriculum material; assessment question and choice translation remains future work.

## QA expectations

Every significant localized frontend feature must be checked in English and Arabic on desktop, tablet, and mobile at 320, 375, 430, 768, 1024, 1280, 1440, and 1920px. Check document language/direction, wrapping, alignment, Arabic typography, arrows and navigation, forms, icon order, cards, artwork, horizontal overflow, and mixed English technical terms. Passing English responsive QA does not establish Arabic parity. See [QA-CHECKLIST.md](QA-CHECKLIST.md).

The current Playwright suite covers all 24 locale routes at the required viewport widths and exercises representative interactions, redirects, query preservation, unknown locales, and metadata. See the dated verification record in [QA-CHECKLIST.md](QA-CHECKLIST.md).

## Current versus target

**Current:** Shared English and Arabic routes live under `src/app/[locale]/`; interface messages are maintained in `messages/en.json` and `messages/ar.json`. Signup, login, verification/resend, password recovery/reset, profile/settings, logout, and safe auth errors have shared EN/AR messages. The URL locale remains authoritative throughout auth. The bundled Inter font passed the initial Arabic visual check at 1280px; responsive review and confirmation of embedded Arabic glyph coverage remain before final Arabic sign-off. Some non-auth hardcoded interface labels, accessible names, and toast messages remain English and are listed in the current QA record; course, lesson, assessment, and event fixtures remain English by design.

**Future:** Separate interface locale, course/source language, and requested AI answer language. Design database-backed localization for courses, modules, lessons, assessments, and certificates with language-independent assessment identity and scoring. No database or AI integration is part of this phase.

## Public marketing site

Public pages use their own typed UI catalog (`messages/marketing/`, see [ROUTES.md](ROUTES.md)) rather than the global next-intl messages, so learner pages do not ship marketing copy to the client. The Phase 09 course catalog and detail request exact-locale database content and never silently fall back; non-course editorial material such as Odoo modules and learning paths may still be English in Arabic pages until their owning phases localize them.
